# Round 01 — 地下城房間與地圖實驗

## 1. 任務目標

本次任務為 Dungeon Lab 的第一輪功能開發。

**目標：建立一個具有基本像素美術、可正常瀏覽的 2D 俯視角地下城房間。**

本輪只實作固定房間的地圖資料、場景渲染與基本網站呈現，不實作角色移動及其他玩法。

Codex 必須遵守專案根目錄的 [`AGENTS.md`](http://AGENTS.md)，並依照其中指定的技術架構、Skills、驗證方式與工作規範進行開發。

### 開發原則

- 嚴格依照本文件實作，不擅自擴充遊戲功能。
- 優先使用專案既有的工程工具與 Skills。
- 保持程式結構簡潔，不提前建立大型遊戲系統。
- 地圖資料與視覺呈現必須分離。
- 本輪成果須可供第二輪自由移動功能使用。
- 不為尚未確定的期末專案需求建立額外架構。

---

## 2. 遊戲呈現方向

### 2.1 基本形式

- 遊戲類型：2D 俯視角地下城。
- 地圖結構：Tile Grid 格子地圖。
- 主要呈現：以房間為核心的探索場景。
- 畫面風格：復古像素地下城。
- 本輪場景：單一固定房間。

格子用於描述地形及通行資訊，**不代表未來角色只能逐格移動**。

第二輪將採用連續座標的自由移動方式。

### 2.2 未來設計方向（本輪不實作）

遊戲未來可能包含：

- 多個地下城房間。
- 連接不同房間的走廊。
- 玩家在房間內自由移動。
- 主動互動與被動條件觸發事件。
- 隨機房間生成。
- 戰鬥、探索與其他遊戲機制。

本輪不需要為以上功能建立完整系統。

## 3. 地圖規格

### 3.1 基本尺寸


| 項目     | 規格           |
| ------ | ------------ |
| 房間數量   | 1            |
| 地圖類型   | 固定矩形房間       |
| 地圖寬度   | 20 格         |
| 地圖高度   | 12 格         |
| 單格邏輯尺寸 | 16 × 16 像素   |
| 地圖世界尺寸 | 320 × 192 像素 |
| 座標原點   | 左上角 `(0, 0)` |
| X 軸    | 向右遞增         |
| Y 軸    | 向下遞增         |


本輪不提供地圖尺寸調整或隨機生成功能。

地圖格子索引以左上角 `(0,0)` 起算，但全域世界座標的 `(0,0)` 位於初始房間幾何中心。兩者應透過座標轉換對應，世界座標支援浮點數與負數。

### 3.2 地圖元素

**地板**

- 房間內主要可通行區域。
- 使用石板地面美術。
- 可以加入少量不影響通行性的紋理變化。

**牆壁**

- 房間四周具有一格厚的外牆。
- 所有牆壁皆不可通行。
- 使用具有一致風格與連接效果的石牆素材。

**障礙物**

- 房間內設置兩組 2×2 格的石製障礙。
- 障礙物不可通行。
- 障礙採不對稱布局，保留足夠的移動空間。

**房門**

- 房間上方中央設置一座兩格寬的封閉房門。
- 房門目前不可通行。
- 本輪不提供開門、互動或房間切換功能。

**預留角色起點**

- 地圖資料中保留角色初始位置。
- 第一輪不顯示角色或起點標記。
- 第二輪可以直接使用該位置初始化角色。

### 3.3 固定地圖配置

使用以下字元表示地圖資料：


| 符號  | 定義           | 可通行 |
| --- | ------------ | --- |
| `#` | 牆壁           | 否   |
| `.` | 地板           | 是   |
| `X` | 石製障礙         | 否   |
| `D` | 封閉房門         | 否   |
| `S` | 預留角色起點，底層為地板 | 是   |


地圖配置如下：

```
#########DD#########
#..................#
#..................#
#....XX............#
#....XX............#
#..................#
#............XX....#
#............XX....#
#..................#
#.........S........#
#..................#
####################
```

### 3.4 位置定義

使用零起始格子座標。

- 外牆：`x = 0`、`x = 19`、`y = 0`、`y = 11`。
- 封閉房門：`(9, 0)`、`(10, 0)`，取代對應外牆格子。
- 第一組障礙：`x = 5～6`，`y = 3～4`。
- 第二組障礙：`x = 13～14`，`y = 6～7`。
- 預留角色起點：`(10, 9)`。

地圖必須嚴格對應以上配置，不得自行重新排列。

`S` 在視覺上顯示為一般地板，不得顯示特殊標記。

## 4. 美術規格

### 4.1 素材來源

優先使用 **Kenney Tiny Dungeon** 素材包。

官方網址：

[https://kenney.nl/assets/tiny-dungeon](https://kenney.nl/assets/tiny-dungeon)

素材風格須保持一致，不得任意混用其他來源的遊戲素材。

若指定素材無法取得，應回報缺少的素材及處理情況，不得擅自替換成完全不同的美術風格。

### 4.2 美術配置


| 元素   | 美術方向          |
| ---- | ------------- |
| 地板   | 暖灰棕色石板        |
| 牆壁   | 灰藍色石磚         |
| 障礙物  | 石柱或石製障礙       |
| 房門   | 與石牆風格一致的封閉門   |
| 裝飾   | 少量破損石板或靜態牆面裝飾 |
| 外部背景 | 深色背景          |


美術要求：

1. 以 16×16 像素圖塊為主要基準。
2. 優先使用整數倍縮放。
3. 採用最近鄰取樣，避免像素模糊。
4. 地板及牆面素材必須正確銜接。
5. 地形與障礙物應具有明確的視覺區分。
6. 美術裝飾不得改變地圖的通行屬性。
7. 不加入動態光照、粒子特效或其他非必要動畫。

本輪不需要人物 Sprite；相關美術保留至第二輪處理。

### 4.3 美術與邏輯分離

地形的可通行性不能由圖片顏色或圖片尺寸決定。

相同地形類型可以對應不同美術變化。

例如不同樣式的地板仍然屬於可通行地形。

牆壁及障礙物的邏輯格子範圍須與地圖資料一致，不得直接以素材外觀決定碰撞範圍。

## 5. 網站與畫面呈現

### 5.1 網站基本版面

網站採用深色簡潔介面，主要視覺空間保留給地下城場景。

建議畫面組成：

1. 頂部網站名稱：`Dungeon Lab`
2. 實驗標示：`Experiment 01`
3. 實驗名稱：`地下城房間測試`
4. 主要地圖顯示區
5. 簡短的地圖資訊：`固定測試房間 · 20 × 12 格`

本輪不需要側邊欄、複雜設定面板、遊戲選單或額外實驗頁面。

### 5.2 地圖呈現

- 房間顯示在主要遊戲區域中央。
- 優先完整呈現整個房間。
- 不得裁切牆壁或重要地形。
- 不得為了填滿畫面而拉伸地圖。
- 保持 20:12 的地圖寬高比例。

建議在桌面環境以 3 倍顯示：

- 顯示寬度：960 像素
- 顯示高度：576 像素

若可用空間不足，則等比例縮小，確保完整地圖仍可顯示。

優先使用整數倍縮放；空間不足時允許等比例非整數縮放，但必須保持像素風格清晰、不變形。

### 5.3 相機規則

本輪採用固定相機。

- 地圖置中。
- 不跟隨任何物件。
- 不提供拖曳、縮放或手動相機控制。
- 不實作角色追蹤。

**未來相機方向：**

當房間能完整顯示時，維持固定相機。

當房間大於可視範圍時，可以根據玩家移動調整相機，但相機必須受到房間邊界限制。

此方向僅供未來開發參考，不屬於本輪驗收要求。

## 6. 地圖資料與程式架構

### 6.1 地圖資料

地圖應具有可被程式讀取的結構化資料，至少包含：

- 地圖寬度與高度。
- 格子地形類型。
- 格子的通行屬性。
- 對應的視覺資源。
- 預留角色起點。

可以使用 TypeScript 的型別及常數資料描述。

本輪不要求通用地圖編輯器、關卡檔案格式或完整地圖管理系統。

### 6.2 資料與顯示分離

必須區分：

**地圖資料層**

負責描述地形、尺寸、位置與通行規則。

**地圖顯示層**

負責讀取地圖資料，使用 Phaser 與對應美術素材繪製場景。

不可只使用一張完整背景圖代替地圖資料。

### 6.3 第二輪銜接

本輪應提供足夠的資料，使第二輪能夠：

- 取得角色初始位置。
- 判斷指定地圖格子是否可通行。
- 找出牆壁及障礙物的位置。
- 使用同一套地圖座標系統加入自由移動。

但第一輪**不實作玩家、移動控制及角色碰撞**。

具體的移動與碰撞機制將由 [`round-02-movement.md`](http://round-02-movement.md) 另行規定。

## 7. 本輪開發範圍限制

### 必須完成

- 可以正常啟動與瀏覽的網站。
- Phaser 遊戲場景。
- 單一固定地下城房間。
- 地圖資料與顯示功能。
- 基本地下城像素美術。
- 正確的地板、牆壁、障礙及封閉門。
- 固定相機與完整房間呈現。
- 基本響應式畫面縮放。

### 不得提前實作

- 角色顯示或移動。
- 碰撞運動系統。
- 戰鬥或怪物。
- 地圖隨機生成。
- 房間切換。
- 走廊系統。
- 門的互動。
- 事件觸發。
- 角色成長或道具。
- 存檔系統。
- 動態光照及非必要特效。
- 後端 API 或資料庫。

除非為完成本輪必要功能，否則不得擴張需求。

## 8. 驗收標準

完成後必須檢查下列項目。

### 8.1 功能驗收

- 網站可正常啟動。
- Phaser 場景能正常載入。
- 正確顯示 20×12 的固定地圖。
- 地圖配置與第 3.3 節一致。
- 地板、牆壁、障礙物及封閉門顯示正確。
- 地圖內部保留預定角色起點資料。
- 地圖資料能正確區分可通行與不可通行區域。
- 地圖資料與美術呈現具有明確的程式分離。

### 8.2 視覺驗收

- 地下城具有一致的像素美術風格。
- 沒有缺圖、素材錯位或明顯的圖塊銜接問題。
- 地圖能完整顯示。
- 地圖縮放後不變形。
- 桌面瀏覽器能正確呈現。
- 視窗縮小時，仍可完整觀看地圖。

### 8.3 工程驗收

- 專案能正常建置。
- 沒有阻礙操作的執行錯誤。
- 使用的技術符合 [`AGENTS.md`](http://AGENTS.md)。
- 未實作本輪禁止的功能。
- 程式結構可供第二輪擴充。
- 保留本輪開發紀錄與驗證成果。

## 10. 最終完成條件

第一輪完成時，Dungeon Lab 應具備：

**一個可在瀏覽器正常瀏覽、具有基本地下城像素美術、使用結構化格子資料建立的單一固定房間。**

這個房間具有牆壁、地板、障礙物、封閉門及預留角色起點。

畫面優先完整顯示房間，地圖資料能提供第二輪自由移動功能所需要的基本地形資訊。

本輪不要求實際可遊玩的角色操作。

第二輪將在本輪完成的地圖基礎上，新增角色與自由移動功能，不重新設計或替換本輪的基本地圖架構。
