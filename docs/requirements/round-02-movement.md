# Round 02 — 角色自由移動與碰撞實驗

## 1. 任務目標

本次任務為 Dungeon Lab 的第二輪功能開發。

**目標：在第一輪已完成的地下城房間中，加入具有基本像素美術、行走動畫、自由移動與碰撞功能的玩家角色。**

本輪必須沿用第一輪的地圖與場景，不得重新建立或替換既有地圖。

Codex 必須遵守專案根目錄的 [`AGENTS.md`](http://AGENTS.md)，並參考 `.agents/skills/` 內的技術指引執行。

### 開發原則

- 嚴格按照本文件實作，不擅自擴充玩法。
- 保留第一輪的地圖布局、美術與網站呈現。
- 使用連續世界座標實現自由移動。
- 移動邏輯、碰撞判定與畫面呈現保持合理分離。
- 優先使用專案既有的 Phaser 技術與工具。
- 不為尚未確定的期末專案需求建立額外系統。
- 完成後必須實際測試並保留工程證據。

## 3. 世界座標系統

### 3.1 座標定義

遊戲採用獨立的連續世界座標系統。

**全域世界原點** `(0, 0)` **固定在初始房間的幾何中心。**

座標方向：

- X 軸向右為正，向左為負。
- Y 軸向下為正，向上為負。
- 世界座標支援浮點數。
- 世界座標支援正數、負數及零。
- 角色移動不受格子中心限制。

角色位置應使用 TypeScript 的 `number` 表示。

世界座標不得直接等同於地圖格子索引或畫面像素座標。

### 3.2 初始房間範圍

沿用第一輪的固定房間：


| 項目     | 數值           |
| ------ | ------------ |
| 地圖格數   | 20 × 12      |
| 單格尺寸   | 16 × 16 世界像素 |
| 房間世界尺寸 | 320 × 192    |
| 左邊界    | X = -160     |
| 右邊界    | X = 160      |
| 上邊界    | Y = -96      |
| 下邊界    | Y = 96       |
| 世界原點   | (0, 0)       |


初始房間橫跨世界座標的四個象限。

未來其他房間也可以位於任意象限，但本輪不建立多房間世界。

### 3.3 地圖索引與世界座標分離

第一輪地圖仍然使用左上角起算的二維陣列索引。

- `col`：從左至右，0～19。
- `row`：從上至下，0～11。

地圖格子中心的世界座標：

```
worldX = (col + 0.5) * tileSize - roomWidth / 2

worldY = (row + 0.5) * tileSize - roomHeight / 2
```

其中：

```
tileSize = 16
roomWidth = 320
roomHeight = 192
```

世界座標對應格子索引：

```
col = floor((worldX + roomWidth / 2) / tileSize)

row = floor((worldY + roomHeight / 2) / tileSize)
```

轉換後必須檢查索引是否位於合法地圖範圍。

注意：以上換算適用於目前位於世界原點的初始房間。未來其他房間若具有不同中心位置，必須先將世界座標轉換為該房間的局部座標，不得直接沿用初始房間的偏移值。

### 3.4 Phaser 座標轉換

Phaser 場景可以保留既有的左上角繪製座標。

本輪應建立明確的座標轉換方式，使世界座標與 Phaser 顯示座標一致。

目前初始房間的轉換為：

```
renderX = worldX + 160
renderY = worldY + 96
```

反向轉換：

```
worldX = renderX - 160
worldY = renderY - 96
```

若使用 Phaser Arcade Physics，可以在既有正座標場景中運行物理系統，再於角色狀態層維持中心原點的世界座標。

不得因為 Phaser 的預設座標方向而取消世界負數座標的支援。

不得將角色世界座標限制成非負數。

### 3.5 座標一致性

角色位置、地圖障礙、碰撞及美術顯示必須維持一致。

不得出現以下問題：

- 角色顯示位置與實際碰撞位置不一致。
- 負座標導致位置錯誤。
- 浮點數座標被強制取整，造成移動跳格。
- 視窗縮放改變角色的世界座標。
- 碰撞判定使用不同的座標原點。

## 5. 角色移動系統

### 5.1 鍵盤控制

支援以下操作：


| 方向  | WASD | 方向鍵 |
| --- | ---- | --- |
| 上   | W    | ↑   |
| 下   | S    | ↓   |
| 左   | A    | ←   |
| 右   | D    | →   |


兩組按鍵具有相同效果，允許混合使用。

同時按住相反方向時，該軸的輸入互相抵銷。

例如：

- W + S：垂直輸入為零。
- A + D：水平輸入為零。
- W + D：向右上移動。
- S + A：向左下移動。

若有其他互不衝突的方向輸入，仍應正常移動。

遊戲接收方向鍵時，應避免瀏覽器因方向鍵而捲動畫面。

### 5.2 移動方式

採用八方向連續自由移動。

角色位置使用浮點數，不進行格子吸附。

移動特性：

- 按下方向鍵立即開始移動。
- 放開所有有效方向鍵立即停止。
- 無加速度。
- 無減速度。
- 無慣性。
- 不提供跳躍或衝刺。

本輪基礎速度固定為：

**64 世界像素／秒。**

不得將速度直接綁定畫面更新次數。

### 5.3 斜向速度正規化

當水平與垂直方向同時具有輸入時，必須正規化移動向量。

移動方向：

```
direction = (dx, dy)
```

若方向向量非零，先將其正規化，再乘上移動速度。

因此：

- 單方向移動速度為 64。
- 斜方向總移動速度同樣為 64。
- 不得因同時按下兩個方向鍵而增加總速度。

### 5.4 時間與幀率

移動結果必須根據經過時間計算。

在沒有碰撞的情況下，相同操作時間應產生近似相同的位移，不應因 30 FPS、60 FPS 或其他畫面幀率而明顯不同。

優先使用 Phaser 既有的時間更新或物理系統。

不得使用每幀固定增加座標的方式實作移動。

## 6. 碰撞系統

### 6.1 碰撞對象

本輪需要阻擋角色的地形：

- 外圍牆壁 `#`
- 石製障礙 `X`
- 封閉房門 `D`

一般地板 `.` 與預留角色起點 `S` 可以通行。

碰撞資訊應讀取第一輪既有的地圖資料。

不得透過分析圖片顏色來判斷碰撞。

### 6.2 角色碰撞體

角色顯示尺寸優先使用 16×16 世界像素。

碰撞體使用較小的矩形，暫定：

```
width = 10
height = 8
```

碰撞體代表角色站立於地面的實際占用範圍。

角色位置定義為碰撞體中心，並視為角色的地面位置參考點。

Sprite 應透過繪製偏移對齊此位置，使碰撞體位於人物的下半身、腳部附近。

不得直接使用整張人物圖片作為碰撞體。

### 6.3 碰撞行為

當角色移動接觸牆壁或障礙時：

1. 不得穿越不可通行區域。
2. 不得進入障礙物內部。
3. 不得穿過封閉房門。
4. 不得移出房間的有效活動範圍。
5. 不得因持續按鍵而出現明顯抖動或彈跳。

角色與障礙接觸時，應保持合理的接觸位置。

### 6.4 沿牆滑動

採用允許沿牆滑動的碰撞方式。

例如同時按住 W+D：

- 若右方受到阻擋、上方可通行，角色仍能向上移動。
- 若上方受到阻擋、右方可通行，角色仍能向右移動。
- 若兩個方向都受到阻擋，角色停止。

不得因斜向碰撞而無條件取消整個移動向量。

優先使用 Phaser Arcade Physics 的碰撞分離能力。

不得使用直接將角色傳送到遠處的方法修正一般碰撞。

### 6.5 碰撞穩定性

角色移動必須避免：

- 高速穿牆。
- 斜向穿過障礙角落。
- 卡入障礙後無法正常離開。
- 持續推牆時畫面抖動。
- 改變視窗大小導致碰撞錯誤。

碰撞邏輯應依世界尺寸運作，不依賴網站的 CSS 縮放比例。

## 7. 角色美術

### 7.1 素材風格

角色採用與第一輪地下城一致的 2D 像素美術。

優先使用：

**Kenney Tiny Dungeon**

[https://kenney.nl/assets/tiny-dungeon](https://kenney.nl/assets/tiny-dungeon)

優先選擇冒險者或騎士造型。

基本要求：

- 角色外觀與地下城素材風格一致。
- 優先使用 16×16 像素角色。
- 使用最近鄰取樣，避免圖片模糊。
- 不任意混用不同視角或解析度風格的角色。
- 角色在地板上應具有合理的大小與位置。

### 7.2 動畫素材要求

**本輪必須實作真正的角色行走影格動畫。**

優先確認 Kenney Tiny Dungeon 是否具有完整、可直接使用的角色動畫影格。

如果原素材不足，可以：

1. 製作風格一致的簡易原創像素行走影格。
2. 使用授權允許的其他免費像素角色動畫素材。

若使用外部素材，必須確認來源、授權與使用限制，並保留來源紀錄。

不得將靜態圖片單純上下晃動、左右旋轉或整體位移，冒充真正的行走影格動畫。

若素材製作或取得存在無法解決的阻礙，應明確回報，不得宣稱行走動畫已完成。

### 7.3 動畫方向

至少提供以下方向：

- 向上行走。
- 向下行走。
- 向左行走。
- 向右行走。

每個方向至少具有 3 個不同的行走影格。

角色停止時，應具有對應面向的待機姿態。

待機姿態可以使用現有行走影格中合適的站立影格，不強制製作額外待機動畫。

### 7.4 動畫播放


| 狀態   | 行為           |
| ---- | ------------ |
| 停止移動 | 顯示對應方向待機影格   |
| 向上移動 | 播放向上行走動畫     |
| 向下移動 | 播放向下行走動畫     |
| 向左移動 | 播放向左行走動畫     |
| 向右移動 | 播放向右行走動畫     |
| 斜向移動 | 使用最接近的主要方向動畫 |


行走動畫建議播放速度為 8 FPS。

動畫應循環播放，直到角色停止移動。

### 7.5 斜向動畫規則

本輪不要求八方向獨立動畫。

當角色斜向移動時，使用四方向動畫中的一個方向表示。

選擇規則：

1. 優先根據實際移動向量判斷。
2. 水平位移絕對值較大時，使用左或右動畫。
3. 垂直位移絕對值較大時，使用上或下動畫。
4. 兩軸位移相同時，優先使用垂直方向動畫。

### 7.6 動畫與碰撞狀態

動畫應依實際移動結果決定，而不只是依據鍵盤是否按下。

例如：

- 按住方向鍵且成功移動：播放行走動畫。
- 按住方向鍵但完全受牆壁阻擋：進入待機。
- 斜向碰撞但仍沿牆滑動：繼續播放對應行走動畫。
- 放開方向鍵：停止行走動畫並保持最後面向。

不得因為按住方向鍵而讓完全靜止的角色持續播放行走動畫。

## 8. 相機與畫面

### 8.1 本輪相機

沿用第一輪的單房間固定相機。

- 房間完整顯示。
- 相機不跟隨角色。
- 不提供拖曳與縮放操作。
- 角色在房間內移動時，地圖保持固定。

### 8.2 畫面縮放

世界尺寸與顯示尺寸應分離。

當視窗縮放時：

- 角色世界座標不改變。
- 移動速度不改變。
- 碰撞範圍不改變。
- 角色與地圖的相對位置不改變。
- 地圖與角色保持等比例縮放。

優先保留第一輪的完整房間顯示方式。

### 8.3 網站介面

保留既有 Dungeon Lab 網站風格。

可以在地圖下方加入一行簡短的操作說明：

`WASD / 方向鍵：移動`

不增加角色狀態面板、設定選單、操作教學視窗或其他 UI 功能。

## 9. 程式實作要求

### 9.1 沿用既有系統

必須優先使用第一輪已建立的：

- 地圖資料。
- 地圖顯示功能。
- Phaser 場景。
- 美術素材管理方式。
- 網站版面與畫面縮放方式。

不得為了加入角色移動而重建整個專案。

若第一輪的程式未具備本輪需要的基本能力，可以進行必要的局部調整，但必須保留原有地圖的外觀、布局與行為。

### 9.2 移動邏輯分離

移動系統應明確區分：

**輸入處理**

取得鍵盤輸入並產生移動方向。

**角色狀態**

保存角色世界座標、面向及移動狀態。

**移動與碰撞**

根據速度、時間及地形阻擋更新角色位置。

**角色顯示與動畫**

根據角色狀態更新 Sprite 與動畫。

可以依照專案規模合理組織程式，不強制建立大量抽象類別或通用遊戲架構。

### 9.3 座標轉換管理

世界座標與 Phaser 渲染座標的轉換應集中處理。

不得在各個程式位置重複散落未命名的 `160`、`96` 等偏移常數。

角色狀態中的位置應明確表示為世界座標。

必要時可建立簡單的座標轉換函式。

### 9.4 禁止過度工程化

本輪不需要：

- ECS 架構。
- 完整角色控制器框架。
- 多角色管理系統。
- 多房間世界管理器。
- 網路同步。
- 通用事件系統。
- 存檔及載入管理器。

只實作本輪必要的系統與功能。

## 10. 驗收標準

### 10.1 角色顯示

- 角色能在初始位置 `(8, 56)` 正確出現。
- 角色美術與地下城風格一致。
- 角色顯示尺寸合理。
- 角色 Sprite 與碰撞體位置正確對齊。
- 待機姿態正常顯示。

### 10.2 移動控制

- WASD 可以正常移動。
- 方向鍵可以正常移動。
- 混合使用兩組按鍵時正常運作。
- 八方向移動正常。
- 角色能停留在任意合法的浮點數世界座標。
- 世界座標支援負數。
- 角色不會自動吸附至格子中心。
- 放開方向鍵立即停止。
- 同時按下相反方向時正確抵銷輸入。
- 斜向總移動速度與直線一致。
- 移動速度不明顯受到 FPS 影響。

### 10.3 碰撞

- 不能穿越外牆。
- 不能穿越兩組石製障礙。
- 不能穿越封閉房門。
- 不能離開有效房間範圍。
- 斜向接觸障礙時能沿未阻擋方向滑動。
- 持續推牆時不會明顯抖動。
- 不會卡入障礙。
- 碰撞不受視窗縮放影響。

### 10.4 動畫

- 具有上、下、左、右四方向行走動畫。
- 每方向至少具有 3 個行走影格。
- 行走動畫能正確循環。
- 停止移動時顯示待機姿態。
- 斜向移動時能選擇適當方向動畫。
- 完全被障礙阻擋時不持續播放行走動畫。
- 沿牆滑動時動畫反映實際移動。
- 動畫沒有明顯閃爍或錯誤切換。

### 10.5 工程與整合

- 第一輪地圖布局保持不變。
- 第一輪美術正常顯示。
- 地圖資料與角色移動系統正確整合。
- 世界座標與渲染座標分離。
- 專案能正常建置。
- 瀏覽器沒有阻礙操作的執行錯誤。
- 未加入本輪禁止的功能。
- 保留必要的工程證據。

## 11. 測試情境

Codex 必須實際執行或透過自動化方式驗證以下情境。


| 測試  | 操作        | 預期結果        |
| --- | --------- | ----------- |
| T01 | 按住 W      | 角色向上連續移動    |
| T02 | 按住 A      | 角色向左連續移動    |
| T03 | 按住 S      | 角色向下連續移動    |
| T04 | 按住 D      | 角色向右連續移動    |
| T05 | 同時按住 W+D  | 向右上等速移動     |
| T06 | 同時按住 W+S  | 垂直輸入抵銷      |
| T07 | 放開所有方向鍵   | 角色立即停止      |
| T08 | 向房間外牆移動   | 角色被阻擋       |
| T09 | 向石製障礙移動   | 角色無法穿越      |
| T10 | 斜向碰撞牆面    | 沿可通行方向滑動    |
| T11 | 朝封閉門移動    | 無法通行        |
| T12 | 移動到世界原點左側 | X 可正常成為負數   |
| T13 | 移動到世界原點上方 | Y 可正常成為負數   |
| T14 | 觀察四方向移動   | 各方向行走動畫正確   |
| T15 | 停止角色移動    | 切換為對應待機姿態   |

測試應包含實際的功能驗證，不得僅以建置成功代表所有操作正確。

若自動化工具無法完整驗證畫布內的操作，應明確區分已自動驗證與尚需人工確認的測試。

## 13. 最終完成條件

第二輪完成後，Dungeon Lab 應具備：

**一個可以在瀏覽器中操作的 2D 地下城房間，玩家能使用 WASD 或方向鍵，以連續世界座標自由移動，並具有正確的碰撞與四方向行走動畫。**

角色位置採用以初始房間幾何中心為原點的世界座標系，完整支援浮點數與負數。

角色可以在房間中自由移動，但不能穿越牆壁、障礙物或封閉房門。

畫面保持第一輪的完整房間固定相機模式。

本輪不實作其他冒險玩法。

完成後應保留兩輪開發的需求文件、[AGENTS.md](http://AGENTS.md)、Git 紀錄、畫面成果與驗證證據，作為第九週作業的工程展示。
